# 文件权限

访问控制的本质就是解决主体（进程绑定的用户凭证）对客体（文件系统中的 inode 及关联数据块）进行操作合法性的判定机制的权限匹配问题。

常见访问权限：
读：从文件中读数据
写：向文件中写数据
执行：将件装入内存并执行
添加：将新信息添加到件结尾部分
删除：删除件，释放空间
列表清单：列出文件名和文件属性

静态的用户和用户组保存在 `/etc/passwd` `/etc/group`中，只有当用户运行程序，成为进程时才会触发权限检查。内核在该进程的PCB中记录了进程继承的身份凭证：

+ UID：当前进程属于哪个用户
+ GID：当前进程属于哪个组

被访问资源中，每个文件/目录都对应一个唯一的inode（索引节点），包含了：
+ i_uid：文件属于哪个用户
+ i_gid：文件属于哪个组
+ i_mode：各类用户对他的操作
  
## UGO权限

+ User：文件所有者（创建文件的用户）
+ Group：与所有者同组的其他用户
+ Others：上述二者之外的用户

对于文件和目录来说，三种权限有所不同：r(读)，w(写)，x(执行)

权限	对文件(-)	对目录(d)
r（读）	可查看文件内容	可列出目录内容（需配合 x）
w（写）	可修改文件	可在目录内创建/删除文件/子目录（需配合 x）
x（执行）	可执行文件（如脚本、程序）	可进入目录（cd）

举例说明

使用`ls -l` 详细列出当前目录文件/文件目录的详细信息：

```bash
-rw-r--r-- 1 zhongpeng zhongpeng 1908 May 28 13:53 CLAUDE.md
```

首行使用 `-` 开头代表这是一个文件，去掉最开始的-后面的九个字符分别对应UGO的对应权限： `rw-`表示User对该文件具有读写权限，同组用户对他有读权限，而其他者也一样，只有读权限。

```bash
drwxr-xr-x 6 zhongpeng zhongpeng 4096 Jun  8 16:16 os
```

开头d表示这是一个目录，后九位是UGO权限，目录的执行表示可以进入的权限。

### 八进制数字表示法

i_mode 中 UGO 的 rwx 实际上由 9 个 bit 存储，每 3 bit 一组（U / G / O），对应一个八进制数字：

每种权限对应一个二进制权重：

| 权限 | 二进制 | 八进制 |
|------|--------|--------|
| r    | 100    | 4      |
| w    | 010    | 2      |
| x    | 001    | 1      |

把每组的三位相加，就得到一个八进制数字：

| 符号   | 计算      | 值 |
|--------|-----------|----|
| `rwx`  | 4+2+1     | 7  |
| `rw-`  | 4+2+0     | 6  |
| `r-x`  | 4+0+1     | 5  |
| `r--`  | 4+0+0     | 4  |
| `-wx`  | 0+2+1     | 3  |
| `-w-`  | 0+2+0     | 2  |
| `--x`  | 0+0+1     | 1  |
| `---`  | 0+0+0     | 0  |

常见权限组合：

| 数字  | 符号           | 含义                         |
|-------|----------------|------------------------------|
| `755` | `rwxr-xr-x`    | 所有者全权，其他人读+执行    |
| `644` | `rw-r--r--`    | 所有者读写，其他人只读       |
| `700` | `rwx------`    | 仅所有者全权                 |

### 权限匹配过程

匹配在内核中进行，由**进程的凭证**比对**文件 inode 的属主**：

```
1. 进程 UID == i_uid  →  用 User 权限位判断，结束
2. 进程 GID == i_gid  →  用 Group 权限位判断，结束
3. 以上都不匹配       →  用 Others 权限位判断
```

关键规则：第一个命中就停止，不向下继续匹配。

用一个反直觉的例子加深理解：

> 文件 owner 权限是 `---`，但 group 权限是 `rwx`，owner 本人能读吗？
>
> **不能。** 因为进程 UID 匹配 i_uid 后直接用 User 的 `---` 拒绝，不会因为 group 有 `rwx` 而放行。

这就是为什么 `chmod` 时要注意：如果把自己锁在门外（`chmod 077`），root 以外谁也救不了。

## chmod 命令

`chmod`（change mode）是用来修改 i_mode 中那 9 个权限 bit 的工具。两种写法：

### 符号模式

```
chmod [ugoa][+-=][rwx] 文件
```

`who`：u（user）、g（group）、o（others）、a（all，即 ugo 三者）
`how`：+ 添加、- 移除、= 精确设置

例子：

```bash
chmod u+x script.sh     # 给 owner 加上执行权限
chmod go-w file.txt     # 去掉 group 和 others 的写权限
chmod a=r report.pdf    # 所有人只读
chmod u=rwx,g=rx,o= gcc # owner 全权，group 读+执行，others 无权限
```

### 八进制模式

把 U、G、O 各算一个数字，直接写到 i_mode 里：

```bash
chmod 755 script.sh     # rwxr-xr-x
chmod 644 file.txt      # rw-r--r--
chmod 700 private/      # rwx------
```

和上文八进制表格完全对应，三个数字就是 U、G、O 各自的 rwx 相加结果。


chmod 做的事情本质上就是：找到文件 inode → 改写 i_mode 里的 UGO 权限位。

## umask：新文件的默认权限

`touch a.txt` 新建文件时，权限是谁定的？

Linux 的规则：**创建文件时有一个原始最大值，再用 umask 掩掉一部分**：

| 类型   | 原始最大值 | 原因                         |
|--------|-----------|------------------------------|
| 文件   | `666`     | 不给 x（文件不应该默认可执行）|
| 目录   | `777`     | x = 能 cd 进去，目录需要     |

`umask` 是一个掩码，**把不想要的权限位扣掉**：

```
最终权限 = 原始最大值 - umask（按位取反后做 AND）
```

查看当前 umask：

```bash
umask        # 通常输出 0022（后三位是 022）
umask -S     # 符号形式：u=rwx,g=rx,o=rx
```

常见 umask 的效果：

| umask | 新建文件 | 新建目录 | 场景       |
|-------|---------|---------|------------|
| `022` | `644`   | `755`   | 默认值     |
| `002` | `664`   | `775`   | 共享项目组 |
| `077` | `600`   | `700`   | 私密环境   |

可以临时修改：

```bash
umask 077          # 当前 shell 生效
touch test.txt     # 结果是 600
```

> **umask 只影响新建**，已有文件的权限只能用 `chmod` 改。

## chown / chgrp：改文件归属

`chmod` 改的是 i_mode（权限位），`chown` 改的是 i_uid 和 i_gid（属主）。

```bash
chown user file           # 改 owner
chown user:group file     # 同时改 owner 和 group
chgrp group file          # 只改 group
```

关键区别：**chown 需要 sudo，chmod 不需要**（前提是文件是自己的）。

```bash
sudo chown alice report.txt          # 把文件转给 alice
sudo chown alice:dev report.txt      # owner → alice, group → dev
sudo chgrp dev report.txt            # 只把 group 改成 dev
```

# 反思

Q：加密保护和访问控制在保障安全时有各自的计算开销。在高性能高并发的分布式文件系统（如 HDFS、Ceph）中，如何权衡这两者的使用？是否可以相互替代？

A：不能相互替代，二者解决的是不同层面的安全问题。

访问控制（ACL/UGO）保护的是「谁能访问」，通过权限检查把不该进的人挡在门外，计算开销很低，只比对元数据，适合集群内部、节点互信的场景。加密保护的是「数据本身」，落盘和传输时对数据加解密，计算开销高（CPU 加解密），适合跨机房传输或合规要求的场景。

权衡策略：

+ 内部环境（HDFS 集群内）：默认信任，用访问控制就够，避免加密拖累吞吐。
+ 跨机房 / 公网传输：加密（TLS/SSL）。
+ 合规场景（金融、医疗）：数据落盘加密（HDFS Transparent Encryption）和访问控制同时用。

Q：在 11408 操作系统真题考点中，目录也是一种特殊的文件。假设用户 userA 对目录 /dir 具有写权限（w），但对该目录下的文件 /dir/test.txt 没有任何权限（即 ---）。请反思：userA 此时能否通过终端强制执行 rm /dir/test.txt 成功删除该文件？请从操作系统目录项（Directory Entry）与文件数据的解耦原理来解释原因。

A：能删除。

删除文件删的不是文件数据，而是目录里的目录项。这两个是解耦的：

目录文件 `/dir` 内部存的是一张目录项表，每一行就是一个「文件名 → inode 号」的映射。比如 `test.txt → 10244`。`rm` 删的就是这一行映射。

而 `test.txt` 本身的 inode（10244）里有它自己的 i_mode、i_uid、i_gid 和数据块指针——这些才是文件内容归属，管的是你能不能读写文件数据块里的内容。

两者的管辖范围完全不同：
+ 文件权限（test.txt 的 i_mode）：管你能不能读写文件数据块。
+ 目录权限（/dir 的 w）：管你能不能修改目录项表（增删条目）。

`rm` 的本质操作是：
1. 修改 `/dir` 的目录项表，把 `test.txt` 那一行删掉 → 需要 `/dir` 的 w ✓
2. 把 inode 10244 的链接计数 -1，计数归零后回收数据块 → 这一步内核自己做，和 userA 无关

整个过程 userA 根本没碰 `test.txt` 的数据，所以文件权限 `---` 不构成障碍。
