突然想到一个关于IO的问题：

如果进程 A 正在等待键盘输入，我这时切换到进程 B（也在等待键盘输入）在进程B的终端中此时键盘输入，内核如何将这次输入事件精准地交给 B，而不会唤醒 A？

分两种情况：
- **同一终端**：A、B 挂在同一个 TTY 等待队列，都会被唤醒，各自检查 PGID。
- **不同终端**：B 的按键只写 pts/1，只唤醒 pts/1 的队列，A 在 pts/0 上根本不受影响。

先解释一下本次学习到的新知识点名词

# 进程组

一组进程的集合，比如像这样：

```bash
cat file.txt | grep "hello" | wc -l
```

shell会开三个不同的进程，分别处理这三个命令，同时使用管道进行通信。

但这三个进程是属于同一个进程组（PGID，同一个作业）

## 前台进程组，后台进程组

先来一个八股定义吧：终端设备上当前拥有键盘输入权和终端信号接收权的唯一进程组。

也就是说，到底谁能接收到键盘输入和中断信号？就是前台进程组。

是由Shell在创建进程时，显式通过 `tcsetpgrp()` 指定的。同一终端同一时刻仅有一个前台。

该组内的进程可以唯一地从终端读取输入；Ctrl+C / Ctrl+Z 等终端产生的信号也投递给该组全体成员。

给后台进程组下一个定义：没有被授予前台读权限的进程，可以有多个或者没有。如果一个进程组属于后台进程组，试图读终端的键盘输入的时候，内核会发一个 `SIGTTIN`信号，阻止他。

## 进程组的创建时机

进程组完全是在我们在终端输入命令时Shell创建的。

创建前台进程组：直接敲命令
创建后台进程组：cmd & （命令后面加一个&符号）

前面提到，如果是创建前台进程组，那么Shell会显式地将调用 `tcsetpgrp(tty_fd, pgid);   // 把 pgid 设为该终端的前台进程组`，创建后台进程组不调用 ` tcsetpgrp()`。

```
用户在 Shell 输入: cat /etc/passwd | grep root

1. Shell 解析命令，准备创建两个进程
2. Shell fork() 出 cat 子进程
3. Shell 在子进程中 setpgid(cat_pid, cat_pid)  → 创建新进程组，cat 为组长
4. Shell fork() 出 grep 子进程
5. Shell 在子进程中 setpgid(grep_pid, cat_pid) → grep 加入同一个进程组
6. Shell 调用 tcsetpgrp(tty_fd, cat_pid)       → 设该进程组为前台进程组
7. Shell 自己 wait() 等待作业结束

此时：cat 和 grep 都是“前台进程组”成员，终端键盘归它们。
```

```
如果用户输入的是: cat /etc/passwd | grep root &

步骤 1-5 完全相同。
步骤 6 跳过（不调 tcsetpgrp）。
Shell 直接输出 "[1] 12345" 并显示下一个提示符。

此时：cat 和 grep 属于“后台进程组”，
      终端的前台进程组仍然是 Shell 自己。
```

# 重新认识键盘输入

键盘输入和屏幕输出是直接作用在TTY伪终端上面的，当我们输入一个字符时，字符最先去的地方是这个TTY的输入缓冲区，这个时候的数据只属于这个终端，不属于任何进程。

而一个TTY只对应一个前台进程组，（内核中使用fg_pgrp记录），只允许这个“前台进程组”的成员读键盘、接收控制信号。

而Shell解释器（比如bash）本身也是一个进程，最初就是运行在你启动的这个终端上的，并且Shell解释器进程是终端的第一个默认前台进程组（对着Shell敲命令）。

Shell解释器的职责：

+ 解析你输入的命令

+ 创建子进程（fork）

+ 用 setpgid() 把子进程编成进程组

+ 向终端申请：把终端的前台权限转交给这个新进程组（tcsetpgrp）

+ 自己进入后台阻塞（wait），等作业结束

+ 作业结束后，Shell 重新把自己设回前台，继续等待输入下一条命令

TTY的输入缓冲区里有了数据。

内核事件会唤醒所有正在这个TTY上等数据的进程。

醒来的进程自己检查（自检）：“我所在的进程组 ID 是不是等于 TTY 记录的那个前台进程组 ID？”

只有前台进程组里的进程，条件满足，于是就从 TTY 的缓冲区里把数据读走。

后台的进程，条件不满足，就会被 SIGTTIN 信号拦下来。

## 为什么内核要唤醒所有的进程让每个进程自检，而不是只唤醒前台进程？

内核要在队列里挑出前台进程再唤醒，就得遍历所有 waiter 查 PGID，成本和全唤醒再自检差不多。与其在内核态做这件事，不如全唤醒，让进程自己检查 — 实现更简单。

# 重新认识等待队列

每一个等待队列只服务于一个特定的等待条件/事件

同一个TTY设备可以挂在多个等待队列

- 读等待队列（等数据可读）
- 写等待队列（等缓冲区有空间可写）

等待队列虽叫"队列"，实际是双向链表，不是 FIFO 排队出队。事件到来时内核遍历链表全唤醒，所有挂在上面的进程同时醒来各自检查条件，不存在"前面进程堵着后面出不来"的问题

# 图形界面下焦点切换到不同终端

在图形界面打开了终端模拟器 A（`/dev/pts/0`）和 B（`/dev/pts/1`），各跑着自己的前台进程。

1. 点窗口 B，显示服务器把"键盘焦点"记成 B。
2. 你按下一个键，显示服务器把按键事件**只发给 B 的终端模拟器进程**，A 那边什么也不知道。
3. B 的终端模拟器收到事件，`write` 到 `/dev/pts/1` 的输入缓冲区。
4. 内核发现 `/dev/pts/1` 缓冲区有数据了，唤醒挂在这个 TTY 读等待队列上的所有进程。
5. 被唤醒的进程自检：PGID == fg_pgrp？是前台的就读走数据，是后台的收 SIGTTIN 被拦。
6. 窗口 A 的 `/dev/pts/0` 全程没收到事件，缓冲区一直空，A 里的进程继续睡，完全不受打扰。
