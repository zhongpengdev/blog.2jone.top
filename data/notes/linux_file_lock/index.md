# Linux文件锁

Linux文件锁主要解决的是多进程访问同一文件时的时序控制和写入先后顺序问题的锁机制。当多个进程同时对同一个文件进行写操作时，就会出现A进程写入的内容被B进程覆盖的现象，也就是说文件的最后状态取决于最后一个写该文件的进程，很显然是不对的。

文件锁(记录锁)就是为了解决当一个进程在写文件时而其他进程就不能对同一文件区域进行修改的机制。实现原理上，既可以锁整个文件，也可以锁文件中的某一个区域，实现不同粒度的锁。

实现文件锁的系统调用有`flock`（系统调用）, `fcntl`（系统调用）以及`lockf`（库函数）。

## 文件锁大致分类

文件锁在应用层主要提供了两种实现机制：
1. 共享锁（读锁）：允许多个进程同时持有并读取文件，但在共享锁未释放前，任何进程不得对文件加写锁。
2. 排他锁（X锁）：同一时刻仅允许一个进程持有。一旦文件被加了排他锁，其他进程不论是试图加读锁还是写锁，都会被系统阻塞或拒绝。

按照内核的拦截力度分类，文件锁大致可以分为：
1. 建议锁（Advisory Lock）：建议锁是文件锁的主流实现，内核只负责记录谁加了锁，但不参与常规 `read/write` 调用的拦截。也就是说，对文件的读写判断完全是由进程自己决定的。
2. 强制锁（Mandatory Lock）：每当进程发起常规的 `read` 或 `write` 系统调用，内核会自动挂起当前进程并检查全局锁表。强制锁比建议锁更安全，但代价就是每次IO读文件前都需要进行检查，并发和吞吐量降低（已废弃）。

```c
#include <sys/file.h>
int flock(int fd, int operation);
```

`flock`只能实现对整个文件加锁，无法实现更细粒度的锁，且只能是建议锁。

如果进程 A 打开了文件并通过 `flock()` 加锁，然后 `fork()` 派生了子进程 B。子进程会复制父进程的 fd 表，但两个 fd 指向的是同一个 `struct file`。由于 `flock` 锁是绑在 `struct file` 上的，父子进程持有的是同一把锁——它们之间不会互斥。但这也会导致任意一方调用 `flock(fd, LOCK_UN)` 解锁，这把锁就对双方都失效了，另一方不会收到任何通知。

`fcntl() / lockf()` 锁粒度更细，可以对文件中某一个范围进行加锁，使得多个进程可以同时修改同一个文件的不同地方，提高了并发度。POSIX 锁绑在 `(inode, 进程)` 二元组 上：内核通过进程的文件描述符表（`struct files_struct`）来识别锁的归属，因此 `fork()` 出的子进程不会继承父进程的锁。

同一进程内通过多次 `open()` 获得的不同 fd 指向同一个 inode，一旦其中任意一个 fd 被 `close()`，该进程在此 inode 上的全部锁都会被释放。

梳理一下lockf大致过程（进程尝试对某个文件加锁时）：

每个文件的索引节点内部有一个专门的标记字段：`i_flctx`（文件锁上下文），上下文内部是一个链表，链表里的每个节点都是一个 `struct file_lock` 结构体。

```c
struct file_lock {
    struct file_lock *fl_next;    // 指向链表的下一个锁对象
    fl_owner_t fl_owner;          // POSIX 锁：进程的 files_struct *；flock 锁：struct file *
    int fl_flags;                 // 锁的来源（FL_FLOCK 或 FL_POSIX）
    int fl_type;                  // 锁状态（F_RDLCK, F_WRLCK, F_UNLCK）
    loff_t fl_start;              // 锁区间的起始字节偏移量
    loff_t fl_end;                // 锁区间的结束字节偏移量
    ...
};
```

当进程尝试对某个文件某区间加锁时，内核遍历 `i_flctx` 链表，检查新区间与已有锁的区间是否重叠。冲突判定如下：
- 已有锁为 `F_WRLCK`（写锁）→ 与任何新锁（读或写）都冲突
- 已有锁为 `F_RDLCK`（读锁）→ 仅与新写锁冲突，新读锁可共存

若冲突且调用的是阻塞版本（`F_SETLKW`），进程进入等待队列（不自旋），等待持有者释放锁后由内核唤醒。若调用非阻塞版本（`F_SETLK`），则立即返回 `EAGAIN`。

## 问题

建议锁的识别粒度取决于具体实现：
- `flock`：最小识别单位是 `struct file`（打开文件描述），非进程。同一进程两次 `open()` 同一文件获得两个 `struct file`，二者之间需要竞争锁。
- POSIX 锁（`fcntl` / `lockf`）：最小识别单位是进程的文件描述符表（`struct files_struct`）。同一进程下的多线程共享同一张 fd 表，因此 POSIX 锁无法区分线程——多线程并发安全仍需依赖应用层的互斥锁（`pthread_mutex` 等）。

## 反思

Q：请反思操作系统中“进程同步”的本质。无论是文件锁、信号量（Semaphore）还是互斥锁（Mutex），它们让进程实现“互斥访问”的最终物理手段，是去修改磁盘上的文件内容，还是去修改内核中进程控制块（PCB）的运行状态（Running/Ready/Waiting）？请用一句话点透锁的底层控制本质。

A：进程同步与互斥的是靠修改内核中进程控制块（PCB）的运行状态实现的，而非修改磁盘或内存中的物理文件内容。

```
[进程 B 执行 flock] ──► 陷入内核 ──► 发现锁冲突
                                      │
                                      ▼
             修改 PCB 状态（Running ──► Blocked/Waiting）
                                      │
                                      ▼
             将该 PCB 从 CPU 就绪队列移出，挂入文件等待队列
                                      │
                                      ▼
             [结果]：调度器不再推入该 PCB，进程 B 的 PC 寄存器（执行流）彻底冻结
```

**锁的本质是：一种借由内核调度器实现的、以“剥夺进程受 CPU 调度机会”为代价的执行流拦截机制。**
